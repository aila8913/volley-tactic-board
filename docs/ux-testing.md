# UX 測試流程

給「兩個以上合理方案、光靠討論分不出高下」的互動/UX 決定用的輕量測試流程（例如
[#214](https://github.com/aila8913/volley-tactic-board/issues/214) 的 rail 彈出 vs 頁面分頁）。
專案目前沒有事件追蹤，做不了正式 A/B 測試，所以用小規模 moderated usability test 代替。

## 什麼時候做

- 兩個方案都做得出來、UX 上各有論點，紙上談兵分不出好壞的時候。
- 不是每個設計決定都要測——顏色/字級這種可以直接用 Artifact 給對方看一眼就決定
  （這個專案一直是這樣做的），測試流程留給「使用者會不會用」這種光憑直覺猜不準的問題。

## 怎麼做

1. **任務情境，不要下指令。** 用「幫我找上一場比賽某位球員的救球數」，不要用「請點球員分析」——
   後者是在測使用者找不找得到入口。
2. **3–5 人，一次只測一個方案**，避免使用者記得另一個方案而互相干擾判斷。
3. **Think-aloud**：請使用者操作時講出「你現在想做什麼、預期會發生什麼」。
4. **記指標**：任務完成時間、點擊/摸索次數、有沒有迷路、測完直接問「比較喜歡哪個、為什麼」
   （開放式，不要引導）。

## 記錄在哪

寫在相關 GitHub issue 底下當留言，不要開新文件——測試結果是一次性的，跟著決策的討論串走才找得到
上下文。[#214 的留言](https://github.com/aila8913/volley-tactic-board/issues/214#issuecomment-5126493974)
是一個範例格式（方案摘要＋檢視清單＋決策規則）可以照抄。

## 決策規則

- 兩案分出高下：直接選完成時間短、錯誤少的那個。
- 打平：優先選學習成本低、跟現有互動一致的那個（複用既有模式比發明新的好）。
