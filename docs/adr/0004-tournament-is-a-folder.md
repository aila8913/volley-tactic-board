# ADR-0004：`tournaments` 是「資料夾」，不是賽事實體

- 狀態：Accepted
- 日期：2026-07-28
- 來源：grill-with-docs 詞彙表建立（CONTEXT.md）過程中，發現表名與實際語意不一致

## 背景

DB 表叫 `tournaments`，但程式碼 181 處與 UI 徽章一律叫它「資料夾」，`ListItemCard.tsx`
甚至寫成「賽事資料夾」把兩個概念疊在一起。表名（賽事）與用法（夾子）長期不一致，
下一個讀 schema 的人很自然會推論「這是賽事實體，該補賽期、主辦單位、賽制欄位」。

這個歧義有實際後果：它決定了往後哪些欄位算合理需求。

## 決定

`tournaments` 的領域本質是**資料夾**——把多場比賽收在一起的分組容器，沒有現實賽事語意。

- **不加**賽期、主辦單位、賽制、分組、名次這類賽事屬性欄位。
- 使用情境是「隨手開個夾子歸檔」，不是「登錄一項賽事」。
- 表名 `tournaments` 維持不動（改名要動 schema push、openapi、前端型別，代價不划算），
  以 `CONTEXT.md` 註明對應關係。

跟 `teams`「只是一個分組標籤，不是複雜的球隊實體」是同一條邊界原則。

## 後果

- 想按賽事維度分析時，靠的是資料夾層級或標籤，不是賽事欄位
- 表名與詞彙表永久不一致，讀 schema 的人得先看 `CONTEXT.md`——這是刻意付的價
- 若日後真要做賽事實體，那是**新概念**（新表、與資料夾並存），不是把這張表長大

## 不要重新提議

- 「`tournaments` 加賽期／主辦單位／賽制欄位」——本 ADR 明確拒絕的那條路
- 「把資料夾正名成賽事、統一 UI 文案」——用法就是夾子，改名只會讓「隨手歸檔」變奇怪
- 「表名改成 `folders` 讓命名一致」——評估過，改動面（schema／openapi／前端型別）不划算
