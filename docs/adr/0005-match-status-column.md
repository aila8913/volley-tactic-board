# ADR-0005：完賽用 `matches.status` 欄位明確記錄，不從局比數推導

- 狀態：Accepted
- 日期：2026-08-05
- 來源：issue #218（一場比賽「結束」的操作節點與畫面）

## 背景

`matches` 原本沒有任何「這場比賽結束了沒」的欄位，取而代之的是一條散在三個地方的推導慣例：

> **sets 陣列的最後一局＝進行中，其餘＝已結束**

- 前端 `lib/volleyballRules.ts` 的 `splitCompletedAndCurrent`（`slice(0, -1)`）
- 後端 `api-server/src/routes/analysis.ts` 的同一條 SQL 版鏡射
- 兩處都有大段註解在說服讀者「這個假設永遠成立」

那段註解自己點名了理由：「schema 沒有『這局結束了嗎』的旗標」。但它真正的意思是**我們無從得知，所以一律當進行中**。代價是：一場比賽打完最後一球之後，那一局仍然被當成進行中，於是**局比數、單場分析頁、資料夾戰績全部少算一局**。

這個代價有實例可循：

- #215 的三戰兩勝比賽在列表被誤標「進行中」。
- 測試資料 `lib/db/src/seed-testdata.ts` 必須在打完的各局之後**補一筆 firstServer=null 的空 set**，才能讓完賽比賽顯示正確——資料被迫造假去遷就一條算錯的規則。
- 計分頁的「結束比賽」只能是一個 `<Link>`：沒有東西可以寫，按下去在資料上不留任何痕跡。

## 決定

加一個 `matches.status`（pgEnum `match_status`，`in_progress` | `finished`，notNull + default `in_progress`），由計分頁的收尾流程明確寫入。

- `splitCompletedAndCurrent(sets, isFinished)` 與後端的 `setResults` 都改吃這個值：已完賽時每一局都是已結束局。
- seed 資料不再補假的空局，形狀跟使用者真的打完一場比賽產生的資料一致。
- 收尾／重新開啟走既有的 `PATCH /matches/{id}`，**不另開端點**——它就是把一個欄位改成另一個值。
- 狀態可逆（PO 決策）：完賽後計分頁照樣進得去，只是唯讀，並提供「重新開啟比賽」改回 `in_progress`。
- 切換狀態後**重新跑一次 `reconstructRecording`**，不在本地手動搬 `currentSet` ↔ `completedSets`。理由是 `CompletedSet` 沒有存 `serving`／輪轉／`serverId`，搬回來的那一局會少掉發球方與輪轉；從 rallies 重放則全部正確還原，也不必維護一套逆運算。

## 後果

- 「這一局算不算完」變成讀一個明確的值，不是猜——這是 #218 真正修掉的東西。
- 多了一個「欄位說已結束，但比分還沒到」的不同步可能。這是刻意接受的：**它正是欄位存在的價值**（棄賽、提前結束這些不靠比分的情況，推導永遠表達不出來）。
- 前後端仍是兩份各自實作的切分邏輯（理由見 ADR-0003：後端聚合留在 SQL），靠註解互相指過去——**改一邊務必同時改另一邊**。
- `abandoned`（棄賽）暫不做：目前沒有任何 UI 會產生它，加了就是死欄位。要做時往 pgEnum 補一個值即可，既有資料不受影響。

## 不要重新提議

- **「用局比數／賽制推導完賽，不要存欄位」**——這正是 #215／#218 的病根，已經付過一次代價。
- **「已打完的比賽補一筆空 set，讓最後一局自然變成 completed」**——舊的 seed 補丁，是用假資料遷就錯規則，已隨本 ADR 移除。
- **「開一支 `POST /matches/:id/finish` 專用端點」**——評估過，改一個欄位用既有 PATCH 就夠，專用端點只多一條路由與一份擁有權檢查。
- **「結束後鎖定不可修改」**——PO 明確決定可逆：記錄者事後對帳是常態，鎖死只會逼人砍掉重記。
- **「達成勝局條件就自動彈出收尾視窗」**——PO 明確決定只做強調提示。記錯一球被強制中斷，比忘記按更惱人。
