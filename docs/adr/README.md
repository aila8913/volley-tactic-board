# 架構決策紀錄（ADR）

這個資料夾放的是**已經拍板、而且不希望被重複討論**的架構決定。

## 什麼該寫成 ADR

判準只有一個：**這個決定被推翻過、或者未來的人看到程式碼會很自然想改回去嗎？**

- 會 → 寫 ADR，把「為什麼不能改回去」留下來
- 不會 → 不用寫。ADR 不是設計文件，也不是進度紀錄

反例：「用 Drizzle 不用原生 SQL」這種沒人想翻案的選型，寫在 CLAUDE.md 就好。

## 什麼時候寫

不要事後補一批。兩個時機：

1. 一個提議被否決，而理由是未來的人需要知道的 → 當下就寫
2. 一個決定經歷過「決定 → 推翻 → 重新決定」→ 當下就寫

## 格式

檔名 `NNNN-短標題.md`，內容三段：**背景 / 決定 / 後果**。目標 30 行以內 —— 長篇分析留在 issue，ADR 只留結論和不可回頭的理由。

狀態用 `Accepted` / `Superseded by ADR-NNNN`。**不要刪除或改寫已 Accepted 的 ADR** —— 被推翻時新增一張並把舊的標成 Superseded，因為「曾經這樣決定過」本身就是資訊。
