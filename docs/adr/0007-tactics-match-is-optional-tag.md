# ADR-0007：戰術的 `matchId` 是可選標籤，不是所屬容器

狀態：Accepted（2026-08-11）

## 背景

`tactics.matchId` 是 #119 加的。當時戰術庫是全域的（A 場存的戰術會出現在 B 場的面板、
切場後按儲存還會覆寫別場），加上 `matchId` 過濾就解決了。當時戰術**只能從某一場比賽進去**，
所以「戰術掛在某場底下」既是實作也是事實，`onDelete: "cascade"` 是對的：刪掉比賽就該
連同它的戰術一起刪，不留孤兒。

#372 推翻了前提。使用情境盤點（`docs/usage-scenarios.md`）裡的 A5「下次遇到他們的快攻，
接發要怎麼站」和 C3「賽前看對手球線分布排佔位」都是**還沒有那一場比賽**就想開板子。
左欄「戰」要能永遠可點，戰術就必須能獨立存在。

## 決定

**`matchId` 降級為可選標籤：`onDelete` 從 `cascade` 改成 `set null`。**
（比照 `teamId` 的處理——team 是可選標籤，match 從今天起也是。）

沒有 `matchId` 的戰術是**一級公民**，不是待清理的孤兒。

## 後果

- 刪掉一場比賽不再連帶刪掉從那場存的戰術，它只是失去標籤。
- 過濾仍然有效：帶 `?matchId=` 就只回那場的，不帶就回全部——#119 要解的跨場汙染沒有回來。
- 代價是 DB 裡會累積一批 `matchId = null` 的戰術，看起來像沒人管的資料。這是預期的，不是缺陷。

反過來的代價才是不能接受的：從八月那場存的一份通用接發站位，之後一直在用，
某天刪掉那場舊比賽時它會**安靜地跟著消失**。不可逆、沒有聲音、使用者事後才發現——
跟 ADR-0006 擋掉的是同一種病。

## 不要重新提議

- **「`matchId = null` 的戰術是孤兒，把 cascade 加回去清一清」**——它們不是孤兒，是全域戰術。
- 「改成 `notNull`，全域戰術用一個特殊的 matchId（0／哨兵值）代表」——把可空性搬進值域，
  每個查詢都要記得排除那個魔術數字。
- 「換成自由標籤（tags）取代 matchId」——已評估：`teams` 已經是更好的分組軸，
  C3 要的是「對上這支隊的戰術」而不是「貼了 #快攻 的戰術」，多一個分組軸只會產生
  兩套互相競爭的分類方式。討論見 #372 留言。
