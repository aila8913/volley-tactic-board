# ADR-0010：進階版補填的記錄模型（手勢、折線、就地升級）

狀態：Accepted（2026-08-12，#21／#51 的 M4 設計討論，拆出 #390–#397）

⚠️ **「後果」段落的「刻意不改簡易版」那一條已被
[ADR-0011](0011-shared-radial-slide-gesture-across-modes.md) 取代**（2026-08-13）：兩個模式改成
共用同一套滑選手勢。其餘決定全部仍然成立。內文原樣保留（Accepted 的 ADR 不改寫、只 supersede）。

## 背景

M4 的 wow 點是「球線分布」。要畫出球線，得先有人把每一觸球的座標記進來——而 `docs/recording-cost-budget.md`
早就證明賽中做不到（live rally 的視線離場預算 ≈ 0 秒），所以進階版一律是**賽後對著影片補填**。

但「補填」這件事在 2026-08-12 之前只有結論、沒有機制：`events` 表的座標／`quality`／`videoTimestamp`／
`source` 全部就位，**卻沒有任何前端在寫它們**，補填介面是零。這份 ADR 記的就是那天把機制定下來的過程。

被記在這裡而不是 issue 留言，是因為以下五條的理由**全都在「為什麼不那樣做」**——而那種東西寫在
issue 裡，issue 一關就等於沒有了（見 CLAUDE.md〈事實住哪裡〉對「ADR 跑進快照／留言」的警告）。

## 決定

### 1. 一觸 ＝ 兩下手勢（滑 ＋ tap），不合併

- **滑**（按住球員 → 滑向動作 → 放開）＝ 誰碰的（`playerId`）＋ 做了什麼（`action`）
- **tap**（點球場上一點）＝ 球去到哪（`toX/toY`）
- **長按滑**（長按 → 滑向得分／失分）＝ 這一分結束了（`rallies.winner`）

三態互斥且完整：**滑 ＝ 有人碰、tap ＝ 球到這、長按滑 ＝ 這分結束**。

### 2. 座標走折線：`from` ＝ 前一觸的 `to`，寫入時複製

一 rally 的軌跡是一條折線，8 觸只要 9 個點（不是 16 個）。`from` 在寫入時從前一觸複製一份存進 DB。
鏈**允許中斷**（對手半場看不清就跳過），中斷處的 `from` 留 `null`。不做 mid 中段點。

### 3. 補填是「就地升級」，不是「並存」

某 rally 若基礎版已記過決定球（`source='live'`），補填時**編輯那一筆**、把它接進觸球鏈，
不新增第二筆代表同一次觸球的 event。`sequence` 因此變成可改。

`source` 的語意是**這筆資料怎麼來的（溯源）**，不是「哪個模式」——升級後那筆維持 `live`，
同一個 rally 混兩種 source 是正常的。

### 4. 動作手動選，不做文法推導

排球的觸球序列幾乎被規則決定（發→接→舉→攻），技術上推導得出 `action`。**PO 否決**：
推導錯而沒被發現會默默污染所有以 `action` 為基礎的統計。降低認知成本改由設計層解決
（顏色分區、不可能的選項灰掉、icon、hover 放大）。

### 5. 影片獨立成表，秒數自動擷取

一場比賽可能有多段影片（一局一段、錄到滿、換電池），`matches.videoUrl` 一欄表達不了 →
`match_videos` 表，`rallies` 存「哪一段 ＋ 第幾秒」。

**不做「對齊」這個獨立步驟**：補填某一分時本來就已經把影片停在那了，該 rally 的第一個手勢
發生時自動擷取當前播放秒數即可。

## 後果

- **`in_play` 第一次有了產生路徑。** 「長按滑」是一分唯一的收尾動作 → 一個 rally 必然剛好一球
  `point`/`loss`、其餘 `in_play`。`schema/events.ts:31` 那條不變量因此**由手勢本身保證**，
  不需要應用層另外檢查。
- **成本**：一觸約 1.3–2.0 秒（定向 tap ＋ 精準座標 tap），8 觸的一分約 10–16 秒，加上暫停倒帶，
  一場 80 分大概是一支影片長度以上的工。這是為了「每一觸都記」付的價，PO 明確接受。
- **進階版的滑方向與基礎版相反**（基礎版是從球員畫線出去、鬆開命中目標）。同一個球場兩種相反
  方向的拖曳，肌肉記憶會打架。**刻意不改基礎版**——那是已經在用的東西，靠模式明確 ＋ 翻轉動畫提示。
- `matches.videoUrl` 刪除（全 repo 無寫入者，值全為 null，無資料要搬）。

## 不要重新提議

- **別把「滑 ＋ tap」合併成一個手勢。** 合併版（按在球的落點、snap 到球員、滑選動作）在
  2026-08-12 當場被否決過，理由是**球的落點 ≠ 球員站位**：接發球時球落在球員前方兩步、攻擊
  起跳點也不是球被打到的那一點。合併會讓一堆觸球 snap 不到任何人、`playerId` 全成 `null`——
  而那是所有個人統計的來源。「看起來更順」換掉的是資料的地基。
- **別改成「live 那筆留著、另外新增整套 review、查詢時忽略 live」。** 它違反
  `schema/events.ts:31` 的不變量（會有兩球是 `point`），而且「有 review 就忽略 live」這條規則
  會散在每一支統計查詢裡——漏一支不是型別錯誤、CI 全綠、數字默默是錯的。那正是 #350／#365／
  #370 反覆踩到的同一個坑。
- **別把 `from` 正規化掉**（改成查詢時 self-join 回前一觸）。它看起來像冗餘資料，但它由
  **單一寫入路徑**產生，不是兩份手寫推導，跟 #370 警告的那種漂移不同類。拿掉它換來的是每一支
  熱圖／球線查詢都要多一次 self-join。
- **別改成「用文法自動推導 action」。** 這在討論當場被提議過並否決（見決定 4）。要提高效率請
  往設計層走（灰掉不可能的選項、分區、icon），不要往「幫使用者猜」走。
- **別把座標改回「正規化 0~1」。** 座標系是 `0–100 × 0–200`（`ScoreSheetCourt.tsx` 的 viewBox，
  與 `schema/events.ts` 註解一致）。#21 舊留言寫的 0~1 是錯的，已在拆票時更正。
- **別把 `quality` 改成純推導值**（「反正距離算得出來」）。`event-grammar-spec.md` 決策 4 已定：
  自動估只是**預設值**，因為 quality 含距離以外系統算不出的因素（高度、旋轉、給不給得起快攻）。
  欄位照存、可手動覆寫。
